- [x] Fixed: `$resultRows += $row` in both `Invoke-GovernedDeletionFromExcel.ps1` and `Find-GovernedCandidatesByScan.ps1` was O(n^2) (PowerShell rebuilds the whole array on every `+=`) - impractical past roughly tens of thousands of rows. Now uses `List[object]` (O(1) amortized `.Add()`). `Write-Progress` calls were also unthrottled per-row; now throttled to the same cadence as the console status line.
- [x] Fixed: worksheet auto-selection (`-WorksheetName` omitted) used to blindly pick the first sheet by position, which broke with ImportExcel's own "does not contain any data in the row/s after the top row of '1'" error whenever that first sheet was an empty cover/instructions tab. `Resolve-GovernedWorksheetName` now checks each sheet's own `Dimension` (a cheap read of metadata EPPlus already tracks, no cell data touched) and picks the first one whose used range extends past the header row.
- [x] Fixed: the write-back used to rebuild the ENTIRE sheet via `Import-Excel` + `Export-Excel -ClearSheet`, which silently reset every column's original Excel formatting (number/date formats, currency, column widths) to ImportExcel's defaults - not just the four new columns'. `Update-ExcelWithResults` now opens the workbook directly (`Open-ExcelPackage`) and edits only the `CleanupStatus`/`CleanupDetail`/`CleanupTimestamp`/`CleanupBy` cells for rows actually processed this run, leaving every other cell (and its formatting) untouched. This also means the write-back cost now scales with rows *processed*, not total rows in the sheet.
- [x] Fixed: reading the candidate Excel used to be a single opaque `Import-Excel` call with zero progress feedback - on a workbook with hundreds of thousands of rows, the console could sit silent for minutes with no way to tell it wasn't hung. `Read-GovernedCandidateRows` now reads row by row via direct cell access (only the path + existing `CleanupStatus` per row, not every column) and reports live "Read N / Total rows" progress the same way every other phase in this package does. As a side effect this also uses less memory than materializing a full typed object per row for every column.
- [x] Fixed a genuine syntax error: `Read-GovernedCandidateRows` built a `[PSCustomObject]@{...}` inline as a bare argument to `.Add(...)`, where one of the hashtable's values (`$ws.Cells[$r, $pathCol].Text`) itself contained a comma inside its own brackets (the multi-arg EPPlus indexer) - that specific combination breaks the PowerShell parser badly enough to cascade into "missing closing brace" errors for the whole function, which meant `Common.ps1` failed to parse at all and every function in it showed as "not recognized." Fixed everywhere in this package by always building the object in a variable first, then calling `.Add($obj)` - never a hashtable literal as a bare method argument. Caught and confirmed fixed by actually installing PowerShell 7 + ImportExcel locally and parsing/running all four scripts for real, rather than relying on visual review.
- [x] Fixed a related bug found by the same real testing: the interactive prompt helpers (`Read-RequiredPath`, `Read-OptionalValue`, `Read-YesNo`, `Read-ActivityTypeChoice`) crashed with "cannot call a method on a null-valued expression" when run from a host with no real console attached (confirmed: `Read-Host` returns `$null`, and - contrary to the obvious fix - `[string](Read-Host ...)` does NOT reliably coerce that to `""`, because a type cast on a pipeline that produced zero output behaves differently from casting a variable that already holds `$null`). Fixed with a shared `Read-HostSafe` helper that does an explicit post-hoc null check.
- [x] Validated end-to-end against real test workbooks (PowerShell 7 + ImportExcel installed locally for this): all four scripts parse cleanly; a full Excel-driven dry run → real quarantine → re-run resume-skip cycle works correctly on real files; multi-sheet auto-detection correctly skips an empty first sheet; and — directly confirming the original formatting bug is fixed — a workbook with a custom currency format, a custom date format, and a custom column width kept all three exactly as-is after the write-back, with the four new columns cleanly appended. **Not** validated here (no Windows host available): `robocopy`-based folder quarantine/delete (robocopy doesn't exist on macOS/Linux - confirmed the error path itself handles this gracefully rather than crashing), the `ActiveDirectory` module owner-inactive check, and a genuinely large (100k+ row) workbook's real-world timing.
- [x] Fixed: a mapped network drive (e.g. `I:\...`) visible in Windows Explorer but reported as "not found" by `Read-RequiredPath` — a Windows elevation quirk (mapped drives aren't shared between an elevated and a non-elevated session), not a script bug. `Read-RequiredPath` now detects a failed drive-letter-style path and prints the explanation plus the fix (match elevation, or use `\\server\share\...` instead) automatically. Documented in the runbook's troubleshooting table too.
- [x] Added `-ThrottleLimit` to `Invoke-GovernedDeletionFromExcel.ps1` (default 1 = unchanged sequential behavior) - processes N rows at once via `ForEach-Object -Parallel` (PowerShell 7+ required), which matters because the per-row cost against a UNC path is mostly waiting on the file server, not CPU. The per-row logic was factored out into `Invoke-GovernedRowEvaluation` in the common engine specifically so the sequential loop and the parallel scriptblock call the identical code, not two copies that could drift apart. CSV log writes are serialized through a shared `Mutex` (threaded through `Write-GovernedLogEntry`/`Invoke-GovernedAction` as an optional `-LogMutex`, zero overhead for existing non-parallel callers); the Excel write-back still happens once, after every row is done. Robocopy's own log file is now named per-thread (`ManagedThreadId`) rather than one shared name, avoiding concurrent-append contention on that file too. Verified with matched 1000-file+2-folder sequential vs. 8-way-parallel runs: identical results (same CSV row count, same Excel status tally, zero duplicate rows) in both, with the parallel run measurably faster even on fast local disk (real network-share latency should show a much larger gap).
- [x] Fixed a real bug surfaced by that same testing (pre-existing, not introduced by the above): `Update-ExcelWithResults`'s `-RowUpdates` parameter was `[Parameter(Mandatory)]`, and PowerShell's parameter binder rejects an *empty* array passed to a Mandatory array parameter outright ("Cannot bind argument ... because it is an empty collection") - which is exactly what happens re-running a file where every row was already resolved by a prior run (0 rows need updating). Fixed by making `-RowUpdates` optional with a default of `@()`.
